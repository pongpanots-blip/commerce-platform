# Winback commerce staff sign-in (stacked on the roles change)

Commerce staff access tokens from `POST /api/admin/auth/login` now authenticate the winback controllers. `sale` can act as a rep; `sales_manager` (including the stored `sale_manager` alias) and `admin` are managers. The database account decides the commerce role, status and password-change requirement on every request. Portal `developer` tokens are rejected even if the account row has since changed role. No refresh-token endpoint is needed by this change.

## Review / PR body notes

- Keep `AdminWriteGuard` so all three existing controller bindings and guard order remain intact. Commerce verification uses AuthModule's exact `PORTAL_JWT_SECRET || 'dev-portal-secret'` configuration and production refusal when the secret is missing. Only `invalid signature` allows Josh fallback; expiry, purpose/type claims, invalid payloads and commerce account failures never fall back. App routes remain auth → sales role gate → ownership.
- Both sources set `req.winbackActor` and the compatible `req.user` claims. `GET /winback/me` exposes canonical `id`, the existing `salesUserId`, `role`, `isManager` and `source`. The legacy unverified bearer decoder remains dev-only and is never used by the role guard.
- Canonical linked rep id is `users.id`. Josh subjects resolve through `winback_staff_links`; an unlinked Josh rep retains their Josh id. Commerce actors optionally carry `joshId`. Link lookups cache hits/misses for 60 seconds; commerce account disabling takes effect on the next request. Josh session/access checks retain their existing 60-second cache and staff.access handling.
- Links and stored-id rewrites commit in one transaction. Visibility compares `actor.id` to the stored owner id using plain equality; there is no new dual-id visibility SQL. The earlier `SalesRepIdentity` report bridge checks links first: a linked account returns only the commerce id; unlinked, uniquely email-matched legacy rows can still use the Josh id temporarily.
- The shared roster selects active commerce `sale`/`sales_manager`/`sale_manager` rows and active internal Josh `sale`/`sales`/`manager` rows without a link. When an active commerce roster entry already reuses the Josh id, the union deduplicates by id and prefers the commerce name/role. Commerce managers expose roster role `manager`. Display names use `users.name` or Josh first/last names with `Staff <8 id chars>` placeholders, never email. Named collaboration directories also resolve admins; public directory outputs remain `{id,name}`. Josh is omitted entirely when legacy auth is off. Assignments, teams, collaboration, analytics and meeting rosters use the same source.
- `1795700000000-WinbackStaffLinks.ts` creates a raw lookup table, following `SalesRepsService`'s raw-table convention, with no ORM entity or relation to Josh copies.
- `winback-staff-backfill` defaults to a read-only, repeatable-read dry-run. `--apply` requires both existing ownership helpers: `WINBACK_OWNER=commerce` and `COMMERCE_OWNS_SALES_REPS=true`. Apply locks staff, link and affected tables while planning and rewriting, refuses conflicting links, overlapping ids and target/natural-key collisions, and rolls back on failure. Run during a maintenance window: table locks block concurrent writes.
- Backfill matches active internal Josh sales reps by lower(trim(email)); Josh admin/platform_admin rows participate only when stored winback identity fields reference them, preserving owner/audit identity. Only active commerce accounts that winback accepts (`sale`, `sales_manager`/`sale_manager`, `admin`) can be matched. Two such accounts with the same normalized email count as ambiguous. A rep whose email belongs only to a developer, disabled or non-sales commerce account is reported as `ineligible` and never linked, so their rows can't move onto an account that can't sign in to winback. The tool doesn't change commerce roles or account status.
- Rewrites cover company assignments, account owners/creators, activity owners, target owners/creators, app-record owners/creators, stage-history actors and meeting acknowledgement actors. Explicit JSON paths cover teams, joint visits, quote events/dispatch actors, daily-report reviewers, opportunity coordination owner ids, collaboration requester/recipient/resolver/from-owner ids, message authors/recipients, and audit targets/owner changes. User-based draft/saved-place/discovery/daily-report keys are rewritten too. Free text, display-name snapshots, customer ids and record ids stay intact. A second run produces zero row rewrites and zero new links.
- Company assignment rewrites publish `company.sales_rep` in the same transaction. The existing winback mirror publishes changed winback rows to Josh with commerce ids. **Josh copies cannot resolve names for ids that differ**; Josh staff ids themselves are preserved for legacy verification/link resolution.
- `winback-staff-accounts-plan` is dry-run only. It proposes role `sale` for Josh sale/sales and `sales_manager` for Josh managers, reuses the Josh id where available, or reports `id taken → new uuid + backfill rewrite` with no concrete id yet. Duplicate normalized emails are excluded as ambiguous. It generates no passwords, creates no accounts, and does not offer an apply mode.
- CLI reports include counts and ids; the account plan includes only masked addresses. Stored payloads, raw emails, passwords and database-driver errors are never printed. `--json` emits the same safe report as compact JSON.

## Cutover sequence (operator actions; not performed by this change)

1. Apply the link-table migration before deploying the new lookup code. Keep `WINBACK_ACCEPT_JOSH_JWT=true` initially (default; `false`, `0`, `off` disable it, ignoring case and surrounding whitespace).
2. Review `npm run winback-staff-accounts-plan -- --json`. Provision missing commerce staff through the existing approved account workflow, preferably reusing Josh ids. Complete the required password change through commerce auth before accessing winback. Check already matching users have an active, allowed staff role.
3. Enable commerce ownership for both winback and company sales reps through the existing cutover process, preventing Josh from overwriting rewritten ids. Review `npm run winback-staff-backfill -- --json`, resolving unmatched/ambiguous identities and collisions.
4. In a maintenance window, run the reviewed backfill with `--apply`. Re-run the dry-run and verify zero planned rewrites. Allow 60 seconds for identity caches to expire (or restart application workers) before reopening the app.
5. Point app sign-in at `POST /api/admin/auth/login`, honor `mustChangePassword`, send the commerce access token, and check `/winback/me` and assignment/collaboration/target ownership. Observe the existing mirror and company assignment outbox. Disable Josh JWT acceptance only after remaining reps have migrated; unlinked Josh reps disappear from directories then.
6. Sessions longer than the commerce access-token TTL (12 hours on master; the refresh-token PR shortens it to `AUTH_ACCESS_TOKEN_TTL_SECONDS`, 15 minutes by default) need the separate `/auth/refresh` PR in the app. This change does not depend on that PR.

No database migrations, backfills or account creation were executed during implementation; database-gated tests were explicitly kept off.
